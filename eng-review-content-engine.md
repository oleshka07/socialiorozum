## Data Model
Таблиці: `workspace, settings_block, prompt_template, source, pipeline_run, step_run, idea, post, content_plan, plan_item, schedule_slot` (див. `db/schema.sql`).

Оцінка: структура коректна, forward-compat поля на місці (`source.origin`, `post.channel_type`, `schedule_slot.status`). Зауваження:
- **`workspace` не має UNIQUE на `name`** → див. блокер B1 (міграція плодить дублі).
- PII: `source.transcript` — це **чутливі дані клієнтів коуча** (зміст терапевтичних/коучингових сесій). Зараз без шифрування, без retention-політики, без доступу. Найвища категорія ризику в продукті.
- Retention: не визначено для `source`/`post`. Треба політика (напр. видаляти транскрипт після N днів, лишати лише згенеровані пости).
- Індекси під поточні запити є (`idx_post_run`, `idx_steprun_run` тощо). Достатньо для очікуваного обсягу.
- БД — чистий Postgres, не Supabase → RLS немає. Авторизація має бути на рівні застосунку (зараз її нема, блокер B2).

## Data Flow
```
[Транскрипт: paste/upload]                         (v3: [сервіс транскрипції] --webhook-->)
        │
        ▼
POST /api/sources ──► source(origin=manual) ──► pipeline_run(status=created)
        │
        ▼  POST /api/runs/:id/steps/:step/run
┌───────────────────────── executeStep(runId, step) ─────────────────────────┐
│ loadSettings(ws) + resolvePrompt(ws,step) → fillPrompt → chat(OpenRouter)   │
│                                                                             │
│ extract_ideas → idea[]      drafts → post(draft)    tone → post(toned)      │
│ format → post(formatted)    deai → post(final)      strategy → plan_item[]  │
│  └─ після кожного: markDownstreamStale(run, step)                           │
└─────────────────────────────────────────────────────────────────────────────┘
        │
        ▼
GET /api/runs/:id ──► {run, steps, ideas, posts, plan}  ──► фронт (кишка)
        │
        ▼  POST /api/runs/:id/schedule
schedule_slot(status=planned)   ──(v3 worker)──►  Telegram автопостинг
```
Потік коректний. Проблема не в напрямку даних, а в **тривалості** одного кроку (див. блокер B3).

## State Machine — `step_run.status`
```
idle ──run──► running ──success──► fresh
  ▲              │                   │
  │              └──error──► error    └── (зміна вище) ──► stale ──run──► running …
```
- Стани: `idle | running | fresh | stale | error`. Термінальний нема (можна перезапускати завжди).
- Тригери: `running` ← виклик API; `fresh` ← успіх; `error` ← виняток; `stale` ← запуск будь-якого попереднього кроку (`markDownstreamStale`).
- **Stuck-стан:** якщо процес упав під час `running`, статус лишиться `running` назавжди — немає таймауту/heartbeat. Треба: при старті кроку перевіряти, чи не висить попередній `running`, або TTL. (середній ризик)

## External Dependencies
| System | Failure mode | Timeout | Retry | Cost/mo |
|---|---|---|---|---|
| OpenRouter | крок падає з `error`, користувач бачить помилку | **не заданий** (fetch без timeout) 🔴 | **немає** 🔴 | змінна; без `max_tokens` і без ліміту — ризик runaway |
| Postgres (internal) | застосунок не стартує (healthcheck у compose) | pool default | pg pool | у межах сервера |
| Hetzner host | все лежить | — | — | фікс/міс |
| (v3) Telegram | пост не публікується | TBD | TBD | безкоштовно |

Дії: додати `AbortController` timeout (напр. 60s) на `fetch` до OpenRouter; retry з експоненційним backoff (max 2-3, jitter); виставити `max_tokens` на кожен крок; денний бюджет-кап.

## Errors & Observability
- Очікувані: OpenRouter 429/5xx/timeout, невалідний JSON від моделі (`extractJsonArray`), порожні вхідні дані (вже кидається явно).
- Зараз помилка лише пишеться в `step_run.error` і повертається 500. Логування — fastify logger (ок), але **немає алертів**. Для продакшну: Telegram-алерт на N підряд помилок OpenRouter.
- **PII в логах:** не логувати `transcript`/контент постів. Зараз не логуються явно — добре, але `chat()` помилки можуть містити фрагмент. Перевірити.

## Security 🔴
- **Trust boundary:** весь API відкритий (`cors origin:true`, без auth). Будь-хто з URL читає чужі транскрипти й палить твій OpenRouter-бюджет. **Блокер B2.**
- AuthN/AuthZ: відсутні. Мінімум на v1-прод — сесійна авторизація + привʼязка `workspace` до користувача, доступ до `run`/`source` лише власнику.
- Secrets: `OPENROUTER_API_KEY` в `.env` на сервері, не в git (✓ `.gitignore`).
- Prompt injection: транскрипт = недовірений вхід, потрапляє в system-промпт як дані. Низький ризик (вихід — текст постів, не дії), але модель може «виконати» інструкції з транскрипту. Помʼякшення: чітко розділяти «це матеріал, не інструкції» в промпті.
- Untrusted input: немає ліміту довжини транскрипту → DoS/вартість. Додати ліміт (напр. 50k символів).

## Test Plan
- **Happy:** sources→run→кожен крок→`fresh`, posts/plan створені; `run-from` перераховує хвіст.
- **Unhappy:** OpenRouter 500/timeout → крок `error`, дані попереднього кроку не зіпсовані (потребує транзакції, блокер B3-supp); модель повертає не-JSON → зрозуміла помилка; порожній transcript → 400.
- **Integration:** реальний OpenRouter-виклик на дешевій моделі; міграція на чистій БД; `docker compose up` end-to-end.
- **Regression:** B1 (один workspace після N рестартів); подвійний клік не дублює пости.
- Покриття: тут немає payment/PII-мутацій ззовні, але транскрипти PII → 100% на шляхах доступу до `source` після додавання auth; 70% решта.

## Performance
- Обсяг на старті: одиниці користувачів, кілька прогонів/день. Навантаження мізерне.
- **Латентність — головна проблема:** один прогін = до ~6×N послідовних LLM-викликів у межах **одного HTTP-запиту**. 6 ідей → ~6 драфтів + 6 tone + 6 format + 6 deai = **24 виклики послідовно** = хвилини. Caddy/проксі обірве на дефолтному timeout, користувач побачить 502. **Блокер B3.**
- N+1: у `executeStep` цикли роблять окремий INSERT на пост — прийнятно за обсягом, але разом з LLM-послідовністю дає довгий запит.

## Rollout & Rollback
- Деплой: `git push main` → GitHub Action → SSH → `docker compose up -d --build`. Простий, ок.
- Rollback: `git revert` + повторний деплой, або `git checkout <prev> && docker compose up -d --build` на сервері. Образи не тегуються версіями → rollback = ребілд попереднього коміту. Прийнятно для старту.
- Міграції: `schema.sql` ідемпотентний (`IF NOT EXISTS`), але **не rollback-safe** і виконується на кожен старт (блокер B1 робить це небезпечним). Для майбутніх змін схеми — окремі нумеровані міграції, не один файл.
- Feature flag/canary: немає. Для одного сервера й кількох юзерів — не критично.
- Smoke-тест після деплою: `curl /health` + один тестовий прогін. Перевіряє людина (Олег), не Claude.

## Edge Cases (≥10)
1. **Подвійний клік «Запустити»** → дві паралельні `executeStep` на одному run: обидві `delete from post` + вставляють → дублі/гонка. Треба блокування на (run, step). 🔴
2. **Мережа впала під час прогону** → крок лишається `running` назавжди (немає таймауту стану).
3. **OpenRouter timeout** → зараз fetch висить без ліміту. Додати AbortController.
4. **Модель повернула текст замість JSON** (кроки 1/7) → `extractJsonArray` кидає; крок `error`, попередні дані цілі лише якщо була транзакція (зараз нема).
5. **Транзакція БД падає між delete і insert** → крок лишає run без постів цієї стадії. Обгорнути крок у `BEGIN/COMMIT`. 🔴
6. **Перезапуск контейнера** → міграція створює ще один `workspace` (B1) → налаштування «зникають». 🔴
7. **Адверсарний транскрипт** (інструкції для моделі / XSS у тексті поста) → фронт екранує (`esc`), але збережений контент треба екранувати скрізь, де показуємо.
8. **Гігантський транскрипт** → перевищення контексту моделі + вартість. Ліміт довжини.
9. **Користувач міняє промпт під час `running`** → результат запишеться зі старою версією; downstream stale спрацює. Прийнятно, але задокументувати.
10. **Дві вкладки, той самий run** → гонка як у п.1 + неузгоджений стан між вкладками (немає realtime). Прийнятно для v1, але знати.
11. **`postIndex` зі стратегії виходить за межі** масиву finals → `finals[idx]` = undefined → `post_id=null`. Вже обробляється мʼяко, ок.
12. **`run-from` на середині, коли попередні кроки не виконані** → крок впаде «немає вхідних постів». Зрозуміла помилка, ок.

## Hidden Assumptions Surfaced
- 🔴 «Кроки швидкі» — насправді один прогін це десятки послідовних LLM-викликів у синхронному HTTP. Обірветься на проксі.
- 🔴 «API внутрішній, auth потім» — але транскрипти це PII клієнтів; відкритий API = витік чужих сесій.
- 🔴 «Міграція ідемпотентна» — `insert into workspace ... on conflict do nothing` без UNIQUE на `name` вставляє новий workspace щоразу; `defaultWorkspace()` бере найстаріший, а seed пише в найновіший → налаштування розʼїжджаються після рестарту.
- 🟡 «Модель завжди поверне валідний JSON» — ні; `extractJsonArray` крихкий.
- 🟡 «Без транзакцій ок» — delete+insert без транзакції лишає неузгоджений стан при збої.
- 🟢 Boring stack (Postgres+Docker+OpenRouter) — правильний вибір, тримаємо.

## Recommendation
**Архітектура й модель даних — валідні, будувати на них можна.** Але перед тим, як давати продукт навіть першому коучу, закрити 3 блокери:

- **B1 (швидко, ~30 хв):** UNIQUE на `workspace.name` + seed-guard у `migrate.ts`, щоб не плодити workspace.
- **B2 (auth, ~0.5–1 день):** мінімальна авторизація (хоч би басік-аут або один токен) + привʼязка run/source до власника. Без цього транскрипти доступні всім.
- **B3 (async, ~1 день):** винести прогін у фонову задачу зі статусом + polling на фронті (або хоча б timeout+retry на OpenRouter і `max_tokens`, якщо лишаємо синхронно з малим N). Плюс транзакція навколо delete+insert у кроці й lock на (run, step) проти подвійного кліку.
